# 0.2 implementation and release assessment

## Current release decision — 2026-09-24

**Semantic evidence accepted for experimental 0.2 by the project owner.** The
[partial-recollection run](../evaluations/2026-09-24-recollection-review.md) demonstrates
useful file associations after reset, pool-hours recall and partial subject recognition.
That level is sufficient for this release. Weak follow-up and unsupported client claims
remain documented limitations, not semantic release blockers. Further policy tuning or
proof of broad reliability is not required for experimental 0.2 acceptance.

The latest mechanical checks pass: 41 tests and both synthetic demos. Release version: `v0.2.0` (2026-09-24). This acceptance does not change individual observations or imply that
every probe was flawless. The assessment below preserves earlier experimental history;
its superseded completeness thresholds do not govern the current release decision.

## Historical assessment

Historical assessment (2026-09-23): unreleased; deterministic implementation is present. Live evaluation is complete for E4B and two Qwen screens and shows semantic failures. No claim that the full release rubric
has passed, no application acceptance claim, and no publication authorization is implied.

## Mechanical evidence

Node 24.14.0 on macOS arm64. `npm run check`, `npm run demo`, `npm run demo:graph`
and `npm run demo:embedded` pass. The test suite covers core admission and atomicity,
plain/fenced decoding through HTTP and in-process adapters, project initialization,
configuration isolation and symlinks, migration, diagnostic rotation/loss, Pi/graph
normalized inputs, and an actual Pi 0.86.0 SDK session using project configuration.
The graph demo runs LangGraph 1.4.16 against a fresh project.

Real child processes are killed during inference, immediately before rename,
immediately after rename, and after commit before delivery. Every boundary preserves
a complete old or new snapshot. Explicit recovery permits later writes without
replaying the interrupted operation. Tests also cover simultaneous recovery attempts,
live owners, PID reuse refusal, foreign/legacy locks and an abandoned coordination gate.

The packed artifact installs offline in a clean consumer. Its CLI initializes and
inspects a fresh project; exported core and graph helpers prepare/observe to revision 2.
Package contents were audited for private study notes, runtime scratchpads and environment
files. Only public implementation, docs and synthetic examples/fixtures are included.

## Frozen protocol

The [rubric](0.2.0-rubric.md) and synthetic cases were recorded before prompt changes.
The old prompt is frozen under tests/fixtures and historical 0.1 traces are unchanged.
The same-harness [0.1 prompt baseline](0.2-baseline.json) contains 13 encounter pairs,
52 model calls, enabled/disabled client responses and provider token counts.
This baseline uses the new decoder/encounter harness with the old prompt; it is not a
binary reproduction of the complete 0.1 runtime.

`npm run eval:semantic` requires an explicitly installed local `FOAM_MODEL` and contacts
only localhost Ollama. It never downloads models or falls back. It defaults to 20
radiator trials, 20 completion trials, ten sequences of ten accesses, and a larger
100-line fixture. `FOAM_TRIALS`, `FOAM_SEQUENCES`, `FOAM_POLICY=0.1` and `FOAM_REPORT`
control counts, baseline and report path. Every result and failure is retained;
semantic scores are left unassigned until review. Provider input/output token counts,
load latency, model digest/quantization, sampling settings and hardware are recorded.

The local runtime is Ollama 0.34.0 on an Apple M4 Max. The harness requests
`think: false`, temperature 0, seed 42, a 16,384-token context and 4,096-token output
reserve. Byte admission includes the complete FOAM request. Token counts are measured
by the runtime after inference; no tokenizer-based preflight is claimed for this harness.
Repeated fixed-seed trials are reproducibility probes, not independent population samples.

Candidate identifiers and the thinking control were verified against the official
[Qwen 0.6B](https://ollama.com/library/qwen3:0.6b),
[Qwen 1.7B](https://ollama.com/library/qwen3:1.7b),
[Gemma E2B](https://ollama.com/library/gemma4:e2b), and
[Ollama thinking documentation](https://docs.ollama.com/capabilities/thinking).
The two Qwen screens and the E4B rerun use the same harness. No model is a preselected winner.

## Findings and release limits

The same-harness baseline has warm prepare p50 2,151 ms / p95 5,238 ms,
observe p50 2,478 ms / p95 3,216 ms, and first-call latency 5,594 ms.
It misses the provisional <3-second interactive preparation p95 target.

Initial 0.2 E4B traces preserve radiator identity and measurement associations in
stored Markdown, but views often paraphrase the current cue. In an ambiguous case,
the view fails to expose which of two radiators needs clarification. The responding
client also fills the field requested to be empty and sometimes claims an unexecuted
note update. Valid JSON is not a semantic pass. These failures must remain in the
release assessment; the prompt is not retuned against these held-out traces.

The enabled/disabled comparison does not yet justify an advantage claim. ACK acceptance
is unverified: no ACK household transcript was used and no message was sent to its
maintainers. A focused retest can use the public synthetic exchange and audit sink.
Safe recovery deliberately retains a manual offline path for a crashed coordination
gate or unknown owner. This is a documented limitation, not automatic recovery from
all possible interruption points. A patch-response policy remains deferred pending
controlled evidence; complete Markdown replacement remains the public contract.

## Focused E4B review

The [agent review](0.2-gemma-e4b-review.json) records each of the 20 radiator and
20 completion trials separately. It is not a blinded human assessment. Distinct
outputs were read directly; exact text grouping avoided rereading duplicates and did
not assign meaning through keyword matching.

| Surface | Reviewed result |
| --- | --- |
| Radiator stored identity / dimension associations | 0 substitutions / 0 reassociations in 20 trials |
| Radiator partial completion at preparation | 4/4 applicable trials omit remaining installation; observation restores it |
| Radiator useful context under the reviewer rubric | 4/20; correction/partial/negative views mostly copy the cue and ambiguous views miss the unresolved referent |
| Enabled radiator client | 0/20 accepted continuations; 4 wrong-field claims of an unexecuted note update |
| Completion in stored Markdown | 20/20 preserved |
| Completion in returned context | 0/20 recalled; all views repeat the old reminder cue |
| Completion in enabled client response | 0/20 recalled |
| Client response instruction (`markdown` empty) | Violated in all 40 enabled and all 40 disabled replies |

The focused semantic gate therefore **fails** even though the protocol returns JSON
with the two expected string fields. This is not evidence of an enabled/disabled
advantage. The thresholds are unchanged, and 0.2 remains an unreleased implementation.

Gemma E2B screening is **not run**. Its verified download was 7.2 GB and the observed
transfer estimate exceeded one hour. The attempt was cancelled and its partial files
removed. The two Qwen candidates were downloaded for the planned local screening.
This is an unmet evaluation item, not evidence that E2B passed or failed.

## Final run counts and latency

The [full E4B run](0.2-gemma-e4b.json) contains 141 encounter pairs and 564 model
calls: 20 radiator, 20 completion, 100 repeated-access and one larger-memory case.
All memory prepare/observe calls completed; two downstream client requests timed out
(drift sequence 8/access 8 enabled, sequence 9/access 5 disabled). They remain failures
in the report and cause the runner to exit nonzero. Both smaller-model screens contain
13 encounter pairs / 52 calls each and no thrown protocol errors; neither passed semantic
screening. See [candidate review](0.2-candidate-review.json),
[Qwen 0.6B traces](0.2-qwen-06b.json) and [Qwen 1.7B traces](0.2-qwen-17b.json).

| Model / policy | Prepare p50 / p95 ms | Observe p50 / p95 ms | First call / model load ms | Large prepare / observe ms |
| --- | ---: | ---: | ---: | ---: |
| E4B / old prompt, 13 pairs | 2,151 / 5,238 | 2,478 / 3,216 | 5,594 / 3,409 | 5,238 / 3,216 |
| E4B / 0.2, 141 pairs | 2,201 / 2,876 | 2,411 / 3,025 | 2,371 / 1 (already warm) | 39,746 / 39,476 |
| Qwen 0.6B / 0.2, 13 pairs | 443 / 11,915 | 476 / 11,758 | 15,273 / 14,637 | 11,915 / 11,758 |
| Qwen 1.7B / 0.2, 13 pairs | 791 / 19,189 | 830 / 16,639 | 16,621 / 15,394 | 19,189 / 16,639 |

The phase summaries omit the first sample of each phase. Different sample mixes make
the p95 columns unsuitable for ranking models directly: one large case dominates a
13-pair screen but not a 141-pair run. E4B meets the numerical mixed-run warm preparation
p95 target, yet the larger-memory profile is unsuitable for the <3-second interactive
target. The old prompt compacted identical fictional activity lines into a grounded
range summary; 0.2 retained them individually. Output length is a major confound.
No response was truncated to improve latency. Model loading is separated from warm
operation time; the E4B full run reused the model loaded for its baseline.

| Run | Request bytes | Response-content bytes | Input tokens | Output tokens |
| --- | ---: | ---: | ---: | ---: |
| E4B old prompt | 112,075 | 19,426 | 21,232 | 5,187 |
| E4B 0.2 | 1,104,400 | 205,897 | 201,379 | 56,229 |
| Qwen 0.6B | 116,875 | 32,981 | 22,548 | 8,708 |
| Qwen 1.7B | 117,067 | 33,716 | 22,607 | 8,914 |

Bytes cover serialized requests and returned content; tokens are provider-reported,
with no output counts available for timed-out client calls. All tested models report
Q4_K_M quantization; raw reports retain exact digests and actual parameter counts
(the E4B runtime reports 8.0B total parameters, Qwen tags report 751.63M and 2.0B).
The full larger request was measured at roughly 2,600–2,719 input tokens, including
instructions and encounter evidence, which together with the 4,096-token output reserve fits the configured
16,384-token context. This observed fit is not preflight tokenizer admission.

Across all ten E4B repeated-access sequences, the prepared and observed Markdown
remained exactly the same reviewed snapshot: unrelated ongoing activities survived
all 100 accesses. None of the views inserted irrelevant sensor content. However, all
50 ferry views merely repeated the ferry cue rather than supplying the known Friday
booking context. These retention successes do not establish useful continuation.

The deterministic implementation is ready for review, with **37 passing tests**, both
required demos and the embedded demo passing, and a final clean packed-consumer check.
The frozen semantic release gate fails, E2B and ACK acceptance remain unverified, and
0.2.0 has not been published. The next iteration needs a revised policy/response
experiment and new held-out cases; this implementation does not silently lower the bar.
